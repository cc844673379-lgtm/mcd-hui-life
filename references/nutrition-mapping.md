# 营养映射规则

营养数据来自 `list-nutrition-foods`，门店菜单来自 `query-meals`。两者是**完全独立的两套体系**：营养数据只有菜名，没有任何商品编码。所有营养结论都必须先经过本文件的映射规则。

## 营养数据字段

`list-nutrition-foods` 返回的每一条只有下列字段：`productName`、`nutritionDescription`、`energyKj`、`energyKcal`、`protein`、`fat`、`carbohydrate`、`sodium`、`calcium`。全部为每份含量，单位为克（能量为千焦与千卡）。

**没有辣度，没有糖分。** 因此辣度与甜度无法由数据推导，本 Skill 不做识别。

## 五道坎

### 坎一：规格被拆开

菜单只给一个商品条目，营养数据却按规格拆成多条。

| 菜单条目 | 营养数据条目 | 处理 |
|---|---|---|
| 可乐 | 可乐中杯、可乐大杯、可乐小杯 | 用 `query-meal-detail` 取默认杯型后再匹配 |
| 玉米杯 | 小杯玉米杯、大杯玉米杯 | 同上 |
| 鲜萃咖啡 | 小杯鲜萃咖啡、大杯鲜萃咖啡 | 同上 |
| 雪碧 | 雪碧中杯、雪碧大杯、雪碧小杯 | 同上 |
| 优品豆浆 | 优品豆浆大杯、优品豆浆小杯 | 同上 |
| 卡布奇诺 | 卡布奇诺中杯、卡布奇诺大杯 | 同上 |
| 燕麦奶 | 冰燕麦奶中杯、大杯、小杯等 | 需区分冷热与杯型 |
| 麦咖啡™奶铁 | 冰奶铁中杯、热奶铁中杯 | 同上 |
| 新地 | 朱古力新地、草莓新地、迷你朱古力新地 | 需用户指定口味 |
| 麦旋风 | 奥利奥麦旋风、草莓麦旋风 | 需用户指定口味 |
| 派 | 香芋派、菠萝派 | 需用户指定口味 |
| 薯条 | 中薯条、大薯条、小薯条 | 需用户指定规格 |

**规则**：菜单名无法唯一定位营养条目时，必须先 `query-meal-detail` 取默认选项；仍无法唯一定位时，请用户指定口味或规格，不得任选一条顶替。

### 坎二：命名不统一

必须归一化后再比对，归一化包含四步：

1. 去除全角括号与半角括号的差异：`纯牛奶（盒装）` 与 `纯牛奶(盒装)` 视为同一项。
2. 去除品牌与系列前缀：`麦咖啡™热美式中杯` 与 `热美式中杯` 视为同一项。
3. 去除空格：`100%苹果汁` 与 `100% 苹果汁(盒装)` 视为同一项。
4. 去除「™」「®」等符号。

归一化后仍不能唯一匹配的，按坎一处理。

### 坎三：新品没有营养数据

以下品类在营养数据中**完全缺失**，随菜单上新还会持续增加：

- 厚松饼系列（枫糖风味厚松饼猪柳堡、猪柳蛋堡及其组合与套餐）
- 吉士蛋麦满分及其组合与套餐
- 芝芝火腿扒堡
- 东南亚风味椰香鸡扒堡
- 龙焰系列（龙焰鸡腿堡、龙焰芝士棒鸡腿堡及各类组合）
- 麦当劳奶昔、茉莉奶绿雪冰、椰奶雪冰
- 【美汁源】多汁柠柠
- 心形薯饼、马苏里拉芝士拉丝条

**规则**：匹配不到就标记为「暂无营养数据」。此类餐品可以参与价格比较（报价接口仍然有效），但输出中**不得出现任何热量、蛋白质、脂肪或钠的数值**，也不得用同类餐品估算替代。

典型情形：某门店最便宜的早餐组合其主品恰好属于缺失品类，此时应如实说明「该组合暂无营养数据，只能比价不能比营养」。

### 坎四：券商品没有营养数据

券对应的商品（如「王牌小食拼」「中薯条买一送一」）是独立商品码，营养数据里没有同名条目。

**规则**：先 `query-meal-detail` 把券商品拆成组成品，再用组成品的营养求和。组成品通常在营养数据中齐全。

拆解时注意：

- `rounds[].choices[]` 中 `quantity` 大于 0 或 `isDefault=1` 的是当前选中项。
- `diffPrice` 为 `+ ¥0` 的选项是等价备选，换算营养时应把它们都算作可选，取营养最优的一条作为推荐，同时保持价格不变。
- 套餐可换项的组合数是各轮可选数的乘积，是双预算优化的主要操作空间。

### 坎五：组合餐名里藏着单品名

组合餐的名称常常包含一个单品名，例如「吉士汉堡包套餐」包含「吉士汉堡包」、「汉堡包开心乐园餐」包含「汉堡包」、「麦辣鸡腿堡三件套」包含「麦辣鸡腿堡」。

**这是一个会造成实际错误的陷阱**：若用名称包含关系匹配，一份套餐会被套上那个单品的营养数据（如吉士汉堡包套餐被套上吉士汉堡包的 294 大卡），而套餐实际还含薯条与饮料，误差可达数百大卡。

**规则**：含「套餐」「件套」「随心配」「随心选」「随心拼」「任选」「分享餐」「双人」「多人」「亲子餐」「乐园餐」「拼盘」「四宫格」「组合餐」「百宝袋」「全家桶」等标记的名称，一律**不参与**单品营养匹配，必须先 `query-meal-detail` 按 `roundList` 拆解为子项，再用子项营养求和。无法拆解时标记为「暂无营养数据」。

## 匹配分层

`nutrition_map.py` 按下列顺序逐层尝试，命中即停。层级越靠前，结论越硬：

| 顺序 | 层 | 判据 | 结论 |
|---|---|---|---|
| 1 | exact | 归一化后完全相同 | 直接采用 |
| 2 | normalized | 去掉包装说明（如「(盒装)」）后相同 | 直接采用 |
| 3 | core | 剥离杯型（中杯/大杯/小杯）与冷热（冰/热）后相同 | 唯一则采用，多个则 `ambiguous` |
| 4 | category | 营养名以菜单名结尾（如「香芋派」以「派」结尾） | 唯一则采用，多个则 `ambiguous` |
| 5 | containment | 菜单名与营养名互为前缀（如「麦辣鸡翅」与「麦辣鸡翅-2块」） | 唯一则采用，多个则 `ambiguous` |

组合餐在进入第 3 层之前就被拦下（见坎五）。

需要特别注意第 3 层与第 4 层的**边界**：只做形态标记剥离与结尾匹配，**不做无约束的子串包含**。否则「奶铁雪冰」会被错配到「奶铁」，把一个风味雪冰当成一杯拿铁咖啡。宁可报 `missing`，也不能给出错的营养数值。

## 脚本用法

`scripts/nutrition_map.py` 完成归一化匹配与缺口统计，纯本地运行，不联网、不调用 MCP。

```text
python scripts/nutrition_map.py --nutrition nutrition.json --menu menu.json --output mapping.json
```

- `--nutrition`：`list-nutrition-foods` 返回的 `data` 字段，可以是原始字符串，也可以是已解析的 JSON。
- `--menu`：`query-meals` 返回的 `data.meals` 映射表，或仅含 `code` 与 `name` 的数组。
- `--output`：可选。写入映射结果与缺口清单。
- 退出码：`0` 表示完成；`1` 表示输入无法解析；`2` 表示参数错误。

输出包含 `matched`、`ambiguous`、`missing` 三组。`matched` 项带 `match_type` 字段，取值与匹配分层一一对应。`ambiguous` 必须人工或经 `query-meal-detail` 消歧后才能使用；`missing` 一律按坎三处理。

### 实测结果（2026-10-12，武汉光谷通信广场餐厅 1960090）

对 `query-meals` 返回的 38 个代表条目运行一次，结果：

| 分组 | 条数 | 说明 |
|---|---|---|
| matched | 16 | 含 13 个 exact、2 个 containment、1 个 normalized |
| ambiguous | 13 | 全部是规格或口味待定项 |
| missing | 9 | 其中 2 项为组合餐，已转交 `roundList` 拆解 |

典型结论：

- `麦辣鸡翅` → `麦辣鸡翅-2块`（containment，菜单名是营养名的前缀）
- `那么大鸡排（椒盐风味）` → `那么大鸡排`（containment，口味后缀）
- `纯牛奶(盒装)` → `纯牛奶（盒装）`（exact，全半角括号归一化）
- `100% 苹果汁(盒装)` → `100%苹果汁`（normalized，去空格与包装说明）
- `燕麦奶` → ambiguous，候选为 `冰燕麦奶中杯`、`热燕麦奶中杯`
- `薯条` → ambiguous，候选为 `中薯条`、`大薯条`、`小薯条`
- `吉士汉堡包套餐` → missing，理由为组合餐需拆解（**不是**套用 `吉士汉堡包`）
- `奶铁雪冰` → missing，**未**被错配到 `奶铁`

## 求和与换算

- 多项组合的营养按组成品的数值直接相加。
- 券商品的营养按 `query-meal-detail` 返回的当前选中组成求和。
- 能量优先取 `energyKcal`；只有千焦值时才用 `energyKj ÷ 4.184` 换算。
- 营养数值一律保留到与原始数据一致的有效位，不做四舍五入凑整。
